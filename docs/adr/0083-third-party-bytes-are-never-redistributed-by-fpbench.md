# 0083 — Third-party bytes are never redistributed by fpbench

*Status: Accepted — 2026-08-08, stage 8E*

## Context

The repository is public. Every byte committed to it is published to anyone who
looks, and stays published: a later deletion does not un-fetch a clone or
un-index a mirror.

Up to Stage 8D the project handled this component by component, correctly but
without a rule. Fingerprint imagery was excluded by `.gitignore` and ADR 0004.
The shaded SourceAFIS jar was excluded because a 27 MB binary is unreviewable.
The NBIS source and binaries live outside the tree because the build is pinned
and certified elsewhere. The learned extractor's checkpoint is excluded because
its licence is unresolved.

Four different reasons for one behaviour. That works until a component arrives
whose licence *does* permit redistribution — an MIT-licensed upstream repository,
say — and then the question "may we vendor this?" has to be argued from scratch,
and the honest answer under the old reasoning is "yes, probably". Which is how a
repository acquires a `vendor/` directory, a stale fork of somebody else's code,
and a provenance story that no longer reduces to a digest.

There is also the enforcement gap. `.gitignore` stops accidents matching patterns
somebody thought of. It says nothing about `git add -f`, and nothing at all about
what is *already* tracked.

## Decision

**Default: `DO_NOT_VENDOR`.** No upstream byte enters this repository, whatever
the licence permits. The question "may we commit this checkpoint?" has one
project-level answer — no, and there is no need — so it does not get asked per
algorithm.

The public repository holds:

```
acquisition code            upstream URLs and identifiers
upstream commit SHAs        exact versions
SHA-256 digests             expected byte sizes
configuration               dependency locks
artifact metadata           provenance records
project-written glue        generated evidence
```

and never holds:

```
a copy of an upstream repository    model weights
a checkpoint                        a runtime bundle
a compiled upstream binary          a dataset
fingerprint images                  extracted embeddings
an upstream archive
```

**Upstream source is a runtime artifact too.** Not just checkpoints. An upstream
repository is acquired at a pinned commit, verified by digest, and kept in the
local store — rather than copied into `integrations/<name>/vendor/`. This both
improves provenance and shrinks the licensing surface, and it is the part that
most often surprises people.

**One local artifact store**, outside the working tree, resolved at runtime from
`FPBENCH_THIRD_PARTY_ROOT` or defaulting to `~/.cache/fpbench/third_party/`. The
repository knows a role, an expected digest, an expected size and an upstream
identity. It never knows an absolute path — a manifest carrying one is a manifest
that works on one machine — and the resolver refuses a store root inside the
checkout.

**Modifying upstream is a ladder**, tried in order: a wrapper that changes no
upstream byte; a project-owned transformation recipe; a local patch. Rungs two
and three are recorded as a preimage digest, the rule, a postimage digest, a
reason and a classification — not as upstream source. A committed fork is what
all three rungs exist to avoid.

**Enforcement is over Git, not over `.gitignore`.**
`fpbench.third_party.repository_guard` reads what Git actually tracks and applies
eight rules: model-weight extensions, known checkpoint filenames, runtime
binaries and bundles, source and artifact archives, dataset and biometric image
formats, directory names whose whole purpose is vendoring, the exact digests of
the upstream artifacts this project already pins, and a one-megabyte ceiling as
the backstop for whatever nobody predicted. Exactly one exception exists and it is
listed by name: the ten synthetic imaging fixtures under `tests/fixtures/imaging/`,
which are checkerboards and gradients generated by a script in that directory.

**CI is held to the same rule, and to two more.** No workflow downloads a
restricted artifact — the public jobs verify contracts, manifests,
digests-as-metadata, synthetic fixtures, source structure and evidence, and
artifact-present verification happens locally. No workflow uploads third-party
bytes as CI artifacts, including from a failing job. And no container image
containing weights, restricted source or a dataset is published to any registry.
All three are scanned for by token in every workflow file.

## Alternatives considered

**Vendor what the licence allows.** Defensible, and it is the path to a `vendor/`
tree that drifts from its upstream digest. It also means asking the question per
component forever.

**Rely on `.gitignore`.** It is a convenience with no authority over tracked
files. Kept, and reported on, but it is not the gate.

**Keep the store inside the repository under an ignore rule.** One `git add -A`
away from publishing a checkpoint.

**Commit small upstream files only.** Every rule with a size threshold gets
argued down. "None" needs no threshold.

## Consequences

Nothing in this repository can be executed without an acquisition step, and that
is intended: the repository describes an experiment rather than shipping one.
A fresh clone runs the contract suites and verifies the evidence; it does not run
an algorithm until the operator fetches the artifacts.

`redistributed_by_fpbench` is `False` in every record and there is no code path
that sets it otherwise. `stored_in_git` and `stored_in_ci_artifacts` are the same.
A caller attempting any of the three gets an error, not a warning.

The guard has a cost: it hashes every tracked file on every run. At this
repository's size that is a fraction of a second, and the alternative — trusting
that nobody ever forced an add — is not a check.
